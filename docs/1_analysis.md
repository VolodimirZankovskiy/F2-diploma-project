# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ІСНУЮЧИХ РІШЕНЬ

## 1.1. Інженерний опис програмних аналогів

Під час дослідження предметної області було проаналізовано три широко розповсюджені інформаційні системи у сфері рекреаційної риболовлі: Fishbrain, Fishing Points та Deeper App.

1. **Fishbrain:** Система перебуває в стадії міграції від монолітної архітектури до Cloud-Native мікросервісів. Взаємодія забезпечується протоколами REST та GraphQL. Стек баз даних включає PostgreSQL, Elasticsearch та Redis. Основним технічним недоліком (Technical Bottleneck) є високий показник затримки (Latency) під час пікових навантажень та наявність технічного боргу в legacy-компонентах.
2. **Fishing Points:** Платформа побудована за сервіс-орієнтованою архітектурою (SOA) із використанням керованих хмарних сервісів AWS (DynamoDB, PostgreSQL). Критичними обмеженнями є висока інфраструктурна вартість та проблеми з узгодженістю даних (Eventual Consistency) при синхронізації офлайн-режимів.
3. **Deeper App:** Рішення базується на подієво-керованій архітектурі (Event-Driven Architecture) з використанням протоколів MQTT, gRPC та WebSockets. Збереження телеметрії реалізовано через MongoDB та TimescaleDB. Недоліком є тісна зв'язність (Tight Coupling) з пропрієтарним апаратним забезпеченням та висока обчислювальна складність конвеєрів обробки батиметричних даних.

## 1.2. Порівняльна інженерна матриця та аналітичний висновок

Для обґрунтування технологічного стеку розроблюваної платформи було побудовано реляційну матрицю порівняння архітектурних метрик конкурентних рішень (Таблиця 1.1).

Таблиця 1.1 — Порівняльна матриця інженерних метрик програмних аналогів
| Система | Архітектурний патерн | Протоколи взаємодії | Стек баз даних (СУБД) | Механізм ML / Аналітики | Індустріальний недолік (Bottleneck) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Fishbrain** | Microservices (refactoring) | REST, GraphQL | PostgreSQL, Redis | Хмарний ML, пропрієтарний | High Latency під час піків |
| **Fishing Points**| Service-Oriented (SOA) | REST API | PostgreSQL, DynamoDB | Агрегація API (без ML) | Висока вартість AWS, синхронізація |
| **Deeper App** | Event-Driven (IoT) | MQTT, gRPC, WSS | MongoDB, TimescaleDB | Обробка часових рядів | Жорстка прив'язка до IoT-хардверу |
| **Проєктована система**| Modular Monolith / Clean Arch | REST API | PostgreSQL, MongoDB | Модель класифікації (scikit-learn)| Усувається на етапі проєктування |

**Аналітичний висновок підрозділу 1.2**

Проаналізовано існуючі програмні рішення у сфері спортивної риболовлі. Виявлено, що використання жорстко зв'язаних архітектур та синхронних REST-запитів у legacy-системах (Fishbrain) призводить до підвищення затримок (Latency) під час масштабування аналітичних модулів. Водночас рішення на базі IoT (Deeper) демонструють надлишкову обчислювальну складність, а системи, що базуються на керованих хмарних інфраструктурах (Fishing Points), характеризуються економічною неефективністю (Vendor Lock-in).

У межах розроблюваної кваліфікаційної роботи передбачено реалізацію архітектури на базі гібридного збереження даних (Polyglot Persistence), де транзакційна цілісність забезпечується реляційною СУБД PostgreSQL, а акумуляція неструктурованих телеметричних датасетів реалізується за допомогою MongoDB. На відміну від аналогів, які переважно використовують статичну агрегацію погодних API, використання стеку Python та FastAPI дозволяє безшовно ізолювати модуль машинного навчання (scikit-learn) для предиктивного аналізу ефективності риболовлі. Це мінімізує навантаження на основний маршрутизатор та дозволяє уникнути проблем із масштабуванням, притаманних конкурентним системам.
