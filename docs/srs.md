# Software Requirements Specification (SRS)
**Стандарт:** ISO/IEC/IEEE 29148  
**Проєкт:** Інтелектуальна аналітична платформа для прогнозування ефективності риболовлі

## 1. System Context (Контекст системи)
Проєктована система є веб-орієнтованою аналітичною платформою, призначеною для агрегації телеметричних логів риболовлі, збору гідрометеорологічних показників та формування предиктивних оцінок ймовірності клювання на базі алгоритмів машинного навчання.

**Межі системи (Scope):**
* **Внутрішній контур:** клієнтський інтерфейс (React SPA/PWA), серверне ядро (FastAPI), модуль предиктивної аналітики (`scikit-learn`), гібридне сховище даних (PostgreSQL + MongoDB) та стек моніторингу (Prometheus/Grafana).
* **Зовнішнє середовище:** користувачі (рибалки-спортсмени та аматори), зовнішній провайдер метеорологічних даних (OpenWeatherMap REST API). Система не здійснює прямого апаратного керування IoT-ехолотами.

## 2. Functional Requirements (Функціональні вимоги)

* **SRS-FUN-01:** Система повинна забезпечувати реєстрацію та автентифікацію користувачів за протоколом OAuth 2.0 / OIDC із видачею підписаних JWT-токенів.
* **SRS-FUN-02:** Система повинна надавати CRUD-інтерфейс для управління профілем користувача та персональним інвентарем (снасті, прикормки) зі збереженням у реляційній СУБД PostgreSQL.
* **SRS-FUN-03:** Система повинна приймати, валідувати (через Pydantic-схеми) та зберігати неструктуровані логи риболовецьких сесій разом із геопросторовими координатами (GeoJSON) у документо-орієнтованій СУБД MongoDB.
* **SRS-FUN-04:** Система має асинхронно отримувати актуальні гідрометеорологічні показники (атмосферний тиск, температура повітря, швидкість та напрямок вітру) від зовнішнього REST API OpenWeatherMap.
* **SRS-FUN-05:** Система повинна виконувати предиктивний розрахунок ймовірності успішного клювання за допомогою попередньо натренованої ML-моделі класифікації (`RandomForestClassifier`) на основі вхідних метеоданих та історичних параметрів.
* **SRS-FUN-06:** Система має надавати агреговані аналітичні метрики (статистика улову за періодами та локаціями) через пагіновані REST-ендпоінти для візуалізації на клієнтській стороні.

## 3. Non-Functional Requirements (Нефункціональні вимоги)

* **SRS-NFR-PERF-01 (Пропускна здатність):** Серверне API повинно витримувати пікове навантаження не менше 500 RPS при горизонтальному масштабуванні контейнерів.
* **SRS-NFR-PERF-02 (Затримка):** Час відгуку API (Latency) на 95-му перцентилі (`p95`) не повинен перевищувати 200 мс для CRUD-операцій та 500 мс для запитів інференсу ML-моделі.
* **SRS-NFR-SEC-01 (Захист даних):** Усі паролі користувачів мають зберігатися виключно у хешованому вигляді за алгоритмом Argon2 або bcrypt; передача даних повинна здійснюватися виключно по захищеному протоколу HTTPS (TLS 1.3).
* **SRS-NFR-SEC-02 (Контроль доступу та Rate Limiting):** API повинно імплементувати обмеження частоти запитів (Rate Limiting: до 100 запитів/хв на одного користувача) та відповідати вимогам OWASP API Security Top 10.
* **SRS-NFR-REL-01 (Відмовостійкість):** Взаємодія із зовнішнім OpenWeatherMap API має реалізовувати патерн Retry з експоненційною затримкою (Exponential Backoff) та таймаутом 3000 мс для запобігання каскадним відмовам.
* **SRS-NFR-OPS-01 (Спостережуваність):** Серверні компоненти повинні експортувати метрики продуктивності (RPS, Latency, Error Rate) у форматі Prometheus.

## 4. Verification Criteria (Критерії верифікації)

| ID вимоги | Метод та інструмент верифікації |
| :--- | :--- |
| **SRS-FUN-01 – SRS-FUN-06** | Автоматизоване модульне та інтеграційне тестування за допомогою фреймворку `pytest` (покриття бізнес-логіки > 80%) та контрактне тестування колекцій у `Postman / Newman`. |
| **SRS-NFR-PERF-01, PERF-02** | Навантажувальне тестування (Load & Spike Testing) утилітою `k6` із фіксацією метрик `p95 Latency` та `RPS` на дашбордах `Grafana`. |
| **SRS-NFR-SEC-01, SEC-02** | Статичний аналіз коду (SAST) через `Bandit / SonarQube` та сканування Docker-образів на відомі вразливості (CVE) сканером `Trivy` у CI/CD пайплайні GitHub Actions. |
| **SRS-NFR-REL-01** | Інтеграційні тести з імітацією таймаутів зовнішнього API (Mocking через `pytest-httpx` / `respx`). |
| **SRS-NFR-OPS-01** | Перевірка доступності ендпоінту `/metrics` та успішного збору (scraping) метрик сервером `Prometheus`. |

## 5. Glossary (Глосарій)

* **Polyglot Persistence** — архітектурний підхід, що передбачає використання різних типів СУБД (у цьому проєкті PostgreSQL та MongoDB) в межах однієї системи відповідно до характеру даних.
* **Latency (p95)** — 95-й перцентиль часу відгуку системи; показник, нижче якого виконується 95% усіх запитів.
* **RPS (Requests Per Second)** — кількість HTTP-запитів, які сервер здатний обробити за одну секунду.
* **JWT (JSON Web Token)** — компактний, криптографічно підписаний формат токенів (RFC 7519) для безпечної передачі даних автентифікації між клієнтом і сервером.
* **ML Inference** — процес застосування вже натренованої моделі машинного навчання до нових вхідних даних для отримання прогнозу.
* **GeoJSON** — відкритий формат кодування географічних структур даних на основі JSON, що підтримується геопросторовими індексами (`2dsphere`) у MongoDB.
